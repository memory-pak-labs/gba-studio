# Electron Compatibility

Este documento registra os requisitos para a GBAStudio Engine ser consumida por uma versao futura do GBA Studio em Electron para macOS, Windows e Linux.

## Principio

O runtime da engine continua sendo C/C++ para Game Boy Advance. A compatibilidade com Electron se aplica ao pacote, ferramentas e scripts que o aplicativo desktop vai chamar via processos externos.

## Contrato Para Electron

- O Electron deve consumir somente o `GBAStudioEnginePack`.
- O app nao deve depender de arquivos privados em `engine/src`.
- Todas as chamadas devem funcionar por caminhos absolutos recebidos por argumento ou variavel de ambiente.
- Nenhum comando deve assumir layout de app macOS, bundle `.app`, Swift, Xcode ou caminho `/Users/...`.
- O build deve ser acionavel por `make -f templates/Makefile.gba` com `PROJECT_DIR`, `ENGINE_PACK`, `TARGET`, `DEVKITPRO` e `DEVKITARM`.
- O `assetc` deve ser chamavel como CLI por `child_process` no Electron.
- O `gbsbuild` deve ser a CLI preferida do Electron para build, encapsulando o Makefile e aceitando caminhos absolutos.
- O `gbsdoctor` deve ser a CLI preferida para diagnostico de Engine Pack, projeto exportado e toolchain.
- O `production_smoke` deve ser a CLI preferida para smoke automatizado de templates e export gerado antes de habilitar fluxos novos no Electron/CI.
- O `stress_projects --json` deve ser chamado antes de habilitar o backend `gbastudio_engine` como beta para usuarios, pois expoe stress por genero, VRAM/OAM, asset banking e audio em formato consumivel pelo Electron.
- O `enginepack.json` deve ser usado pelo app para descoberta de ferramentas e capacidades.
- A selecao de tipo de projeto deve usar `engine_manifest.sdk_templates` retornado pelo `gbsdoctor --json`, cobrindo `topdown_basic`, `platformer_basic`, `isometric_basic`, `point_click_basic`, `shmup_basic`, `visual_novel_basic`, `menu_basic`, `cutscene_basic` e `world_map_basic` sem acessar arquivos privados.
- O Electron pode validar entradas de export com `engine_manifest.schemas.export_project` antes de chamar `assetc --export-project-json`; para top-down simples, o bloco `topdown_project` ja gera `gbastudio_project_data.hpp` com rooms, colisao, portais, metadata de room, NPCs, triggers, choice groups, scripts simples de room/portal/interacao/NPC/trigger/escolha, player e camera sem escrever C++ manualmente. Para plataforma, `platformer_project` ja gera `platformer_project_data.hpp` com rooms, colisao, player start, camera, config fisica, hazards, checkpoints, camera zones e scripts de sala/hazard/checkpoint/zona. Para isometrico, `isometric_project` ja gera `isometric_project_data.hpp` com rooms, grid, camera, colisao, atores iniciais e scripts de room/ator. Para apontar e clicar, `point_click_project` gera `point_click_project_data.hpp` nativo com cenas, hotspots, cursor, inventario por variaveis, `give_item`, `required_item`, `unavailable_line`, `on_use_item`, `save` para persistir cena/cursor/item/variaveis, HUD de cena/item selecionado, dialogo, scripts e backgrounds opcionais. Para shoot-em-up, `shmup_project` gera `shmup_project_data.hpp` nativo com player, projeteis, waves, inimigos, scripts, `save` para persistir score/high score, vidas, wave, posicao e variaveis, e backgrounds opcionais. Para visual novel, `visual_novel_project` gera `visual_novel_project_data.hpp` nativo com cenas, textos, choices condicionais por variavel, `on_select`, destino por escolha, historico simples, `save` para persistir cena/historico/variaveis, HUD de cena/historico, scripts e backgrounds opcionais. Para menu/UI, `menu_project` gera `menu_project_data.hpp` nativo com telas, stack de submenu, itens condicionais, itens escondidos quando indisponiveis, toggle/slider por variavel, `save` para persistir tela/stack/variaveis, HUD de tela/item/stack, scripts e backgrounds opcionais. Para cutscene, `cutscene_project` gera `cutscene_project_data.hpp` nativo com cenas, passos temporizados, branch por variavel, skip controlado, `on_skip`, espera por dialogo, `save` para persistir cena/step/variaveis, HUD de cena/step/frame, scripts e backgrounds opcionais. Para mapa mundial, `world_map_project` gera `world_map_project_data.hpp` nativo com nos, conexoes direcionais por indice/nome, selecao de level, nos condicionais por variavel, feedback de bloqueio por `locked_line`/`on_locked`, nos escondidos por `hide_when_locked`, `save` para persistir progresso de campanha, dialogo, scripts e backgrounds opcionais. Os blocos aceitam `includes`, `assets`, `resource_banks`, `resource_bank_groups` e `rooms[].resource_bank_group` para ligar headers, simbolos C++ gerados por `assetc` e planos deterministas de VRAM/OAM; quando houver `asset_pack`, `assets.bg_palettes`, `assets.obj_palettes`, `assets.tile_assets` e `topdown_project.backgrounds[].tilemap` podem referenciar assets por ID, e o exportador inclui automaticamente os headers gerados. `resource_banks: "asset_pack"` gera os bancos a partir de `asset_pack_report.resource_bank_plan` e tambem emite `ResourceBankUploadSource[]` para os dados de tiles/paletas gerados. O campo `asset_pack.assets[].bank_group` alimenta `asset_pack_report.resource_bank_groups[]`, que o `assetc` tambem materializa como `gbs::ResourceBankGroup` no `ProjectData`; cada room pode apontar para um grupo pelo nome para o Electron mostrar/planejar bancos por room, area ou conjunto compartilhado.
- O `gbastudio_project_data.hpp` deve ser tratado como arquivo gerado pelo exportador, consumido por template C++ estavel.
- Para o app Swift atual e para uma versao futura em Electron, o caminho recomendado e normalizar o projeto em uma estrutura equivalente a `RoomRuntimeSpec` e so entao gerar `gbastudio_project_data.hpp`.
- Assets de audio PSG, tracker PSG, MOD ProTracker subset com volume/finetune, tempo, arpeggio, slides, portamento, vibrato, tremolo e pattern jump/break aproximados, samples MOD/S3M extraidos para PCM com loop points, S3M subset com volume de instrumento, speed/tempo/slides/portamento/vibrato/tremolo aproximados e pattern jump/break, VGM SN76489 subset com volume/noise e skips seguros para stereo/data blocks, PCM 8-bit assinado e WAV PCM mono/stereo 8/16-bit sao convertidos para dados C++ estaticos no projeto exportado. Samples S3M 8/16-bit mono/stereo nao comprimidos sao normalizados para PCM8 mono. O runtime mixa ate 4 SFX PCM simultaneos com prioridade/volume mais uma trilha PCM de musica em stream por blocos.
- Efeitos de render como affine BG2/BG3, affine OBJ estatico ou por keyframes, modos bitmap 3/4/5, alpha/brightness blending, mosaic com enable por BG/OBJ, window0/window1 e OBJ window podem ser declarados pelo exportador como chamadas ao runtime; VRAM banking dinamico continua fora do subset atual.
- Para projetos maiores, o Electron deve usar as capacidades `render_asset_cost_diagnostics`, `audio_mix_cost_diagnostics` e `template_production_cost_smoke` do `enginepack.json` antes de habilitar exports que dependem de diagnostico de producao. Os helpers publicos `RenderAssetCost` e `AudioMixCost` permitem estimar bytes, tiles, screenblocks, OAM, PCM, mixer frames e vozes diretamente nos templates gerados, sem acessar `engine/src`.
- Resource managers em headers publicos permitem que o exportador reserve/libere tilesets, bancos de paleta e OAM por asset, banco ou grupo antes de emitir chamadas de load; `reserve_resource_batch`, `release_resource_batch`, `reserve_resource_banks`, `release_resource_banks`, `reserve_resource_bank_group` e `release_resource_bank_group` oferecem ciclo transacional de carga/descarga de assets de room/export, e snapshots/rollback permitem abortar cargas parciais ou releases inconsistentes de rooms/bancos sem heap. Para streaming maior, `ResourceBankCache` e `reserve_resource_bank_cached` permitem cache estatico por prioridade/recencia com eviction de bancos desbloqueados e rollback completo quando a reserva nao couber; `hot_swap_resource_bank_group` permite trocar grupos de room preservando rollback e nome do grupo ativo, e `stream_resource_bank_group` combina reserva inicial/no-op/hot-swap com scratch buffer estatico para templates que trocam room. `enqueue_resource_bank_upload_vblank`, `enqueue_resource_bank_uploads_vblank` e `enqueue_resource_bank_upload_sources_vblank` agendam as copias para VRAM/paleta/OAM na fila DMA de VBlank; a variante por `ResourceBankUploadSource` permite que o Electron gere fontes em qualquer ordem e o runtime combine por nome de banco. `capture_engine_resource_usage` expõe capacidade, uso, restante e maior bloco livre para diagnostico exibivel no Electron. Os exports JSON `topdown_project`, `platformer_project` e `isometric_project` aceitam `resource_banks`, permitindo que Electron/GBA Studio passem um plano deterministico de bancos para os templates sem acessar codigo privado da engine.
- Os templates top-down, platformer e isometrico empacotados streamam automaticamente o `ResourceBankGroup` da room inicial, do restore de save e das trocas de room quando `ProjectData::resource_bank_groups` existe; se o header exportado tambem inclui `ResourceBankUploadSource[]`, eles usam `stream_resource_bank_group_with_uploads` para enfileirar uploads de tiles/paletas/OAM por DMA de VBlank e receber `ResourceStreamResult` com diagnostico de banco/pool quando algo falha. Se o projeto nao usa grupos, eles preservam `reserve_resource_banks` global e fallback por `reserve_resource_batch`. O Electron pode usar `gbsdoctor`/`enginepack.json` para exigir `assetc_resource_bank_plan`, `assetc_resource_bank_groups`, `resource_bank_group_reservation`, `resource_bank_group_hot_swap`, `project_resource_bank_groups`, `project_resource_bank_group_lookup`, `project_room_resource_bank_group_binding`, `template_room_resource_bank_group_streaming`, `template_room_resource_bank_group_upload_streaming`, `resource_bank_group_upload_streaming`, `resource_stream_diagnostics`, `resource_bank_named_upload_sources`, `asset_export_resource_banks_from_asset_pack`, `asset_export_resource_bank_groups_from_asset_pack`, `asset_export_resource_bank_upload_sources`, `asset_export_semantic_asset_refs`, `asset_export_semantic_audio_refs`, `asset_export_semantic_actor_refs`, `asset_export_semantic_isometric_actor_refs`, `asset_export_semantic_platformer_enemy_refs`, `asset_export_semantic_platformer_platform_refs`, `topdown_resource_batch_reservation`, `platformer_exported_resource_banks` ou `isometric_exported_resource_banks` antes de gerar projetos que dependam desse fluxo.
- O template `platformer_basic` empacotado comprova o primeiro runtime multi-genero. O Electron pode exigir `platformer_runtime`, `engine_sdk.platformer_project_data_contract` e `asset-export-platformer-project-data` no manifesto antes de exportar projetos de plataforma e gerar `platformer_project_data.hpp` com `const gbs::PlatformerProjectData project`, sem acessar codigo privado da engine. Projetos de plataforma tambem podem exigir `platformer_runtime.hazard_regions`, `platformer_runtime.checkpoint_respawn`, `platformer_runtime.platformer_camera_zones`, `platformer_runtime.event_scripts`, `platformer_runtime.enemy_event_scripts`, `platformer_runtime.moving_platform_event_scripts`, `platformer_runtime.slope_floor_snap`, `platformer_runtime.actor_animation_state`, `platformer_runtime.enemy_stomp_contact`, `platformer_runtime.enemy_tile_patrol`, `platformer_runtime.moving_platform_landing_snap`, `platformer_runtime.room_warp`, `save.platformer_save_payload` e `save.platformer_autosave_on_progress`.
- Para projetos de plataforma com inimigos ou plataformas moveis, o Electron deve exigir `platformer_runtime.enemies` e `platformer_runtime.moving_platforms`. O export JSON aceita `rooms[].enemies[]` com bounds/patrol/velocidade/dano e `rooms[].moving_platforms[]` com bounds/start/end/velocidade; ambos aceitam visual por `metasprite`/`sprite`/`sprite_asset`/`asset` vindo do `asset_pack`, gerando arrays estaticos no `PlatformerRoomData`; inimigos aceitam `on_hit`/`on_touch`/`on_hit_player`, o runtime diferencia stomp de dano lateral e pode virar em parede/borda por `update_platformer_enemy_patrol`, e plataformas moveis aceitam `on_stand`/`on_contact`/`on_ride`/`on_touch` para scripts por objeto com carry e landing snap; o template copia esses dados para buffers fixos por room e atualiza sem heap.
- O template `isometric_basic` empacotado adiciona o terceiro caminho de genero. O Electron pode exigir `isometric_runtime`, `engine_sdk.isometric_project_data_contract` e `asset-export-isometric-project-data` antes de exportar grids isometricos e gerar `const gbs::IsometricProjectData project` com atores ordenaveis por depth sem acessar codigo privado da engine. Exports isometricos tambem podem exigir `isometric_runtime.iso_tilemap_collision`, `isometric_runtime.iso_diamond_picking`, `isometric_runtime.iso_greedy_path_step`, `isometric_runtime.iso_bfs_path_step`, `isometric_runtime.iso_astar_path_step`, `isometric_runtime.event_scripts`, `isometric_runtime.tile_event_scripts`, `isometric_runtime.tile_event_areas`, `isometric_runtime.cursor_selection`, `isometric_runtime.cursor_actor_interaction`, `isometric_runtime.actor_command_apply`, `isometric_runtime.room_cursor_start`, `isometric_runtime.tactical_core`, `isometric_runtime.room_warp`, `save.isometric_save_payload` e `save.isometric_autosave_on_progress`.
- O template `exported_menu` empacotado comprova o runtime nativo v4 de Menu/UI. O Electron pode exigir `menu_runtime`, `engine_sdk.menu_project_data_contract`, `runtime_profiles.menu_native_contract`, `asset-export-menu-project-data`, `menu_screen_stack`, `menu_item_conditions`, `menu_toggle_items`, `menu_slider_items`, `menu_save_data`, `menu_autosave_slot0`, `menu_hud_screen_stack`, `menu_text_input`, `menu_text_input_keyboard` e `save.export_project_config` antes de exportar menus, telas de UI, opcoes persistentes e fluxos simples de selecao com `MenuProjectData`.
- O template `exported_cutscene` empacotado comprova o runtime nativo v4 de Cutscene. O Electron pode exigir `cutscene_runtime`, `engine_sdk.cutscene_project_data_contract`, `runtime_profiles.cutscene_native_contract`, `asset-export-cutscene-project-data`, `cutscene_branch_steps`, `cutscene_step_skip_control`, `cutscene_wait_for_dialogue`, `cutscene_save_data`, `cutscene_autosave_slot0`, `cutscene_hud_scene_step` e `save.export_project_config` antes de exportar cenas lineares ou ramificadas com progresso persistente em `CutsceneProjectData`.
- O template `exported_shmup` empacotado comprova o runtime nativo v4 de Shoot-em-up. O Electron pode exigir `shmup_runtime`, `engine_sdk.shmup_project_data_contract`, `runtime_profiles.shmup_native_contract`, `asset-export-shmup-project-data`, `shmup_save_data`, `shmup_autosave_slot0`, `shmup_hud_score_lives_high_score` e `save.export_project_config` antes de exportar jogos de nave/tiro com HUD e progresso persistente em `ShmupProjectData`.
- O template `exported_world_map` empacotado comprova o runtime nativo World Map v4. O Electron pode exigir `world_map_runtime`, `engine_sdk.world_map_project_data_contract`, `runtime_profiles.world_map_native_contract`, `asset-export-world-map-project-data`, `world_map_conditional_nodes`, `world_map_locked_feedback`, `world_map_hidden_nodes`, `world_map_save_data`, `world_map_hud_node_status` e `save.export_project_config` antes de exportar mapas de fases com nos conectados, cursor, scripts de selecao, desbloqueios por variavel, HUD de status e save de progresso.
- Para pathfinding isometrico que precisa contornar obstaculos, o Electron pode exigir `isometric_runtime.iso_bfs_path_step` ou `isometric_runtime.iso_astar_path_step` e limitar o orcamento de busca por ator/room antes de chamar `find_iso_path_step_bfs` ou `find_iso_path_step_astar`.
- Tilemaps exportados podem escolher dados brutos, RLE 16-bit ou LZ77 por CLI, e tiles 4bpp/paletas podem escolher `assetc --lz77-tiles` ou `assetc --lz77-palette` quando o exportador quiser reduzir dados estaticos mantendo fallback bruto no header; o Electron continua como orquestrador sem depender de codigo privado da engine.
- NPCs exportados podem declarar movimento simples (`patrol`, `wanderBox`, `followPlayer`, `pathToPoint`) em `gbastudio_project_data.hpp`; o app deve validar bounds/alvos e limitar pathfinding para evitar custo excessivo no GBA.
- Para follow/path de NPCs, o Electron pode montar a mesma lista fixa de blockers usada na colisao e chamar `find_actor_path_step_with_actor_collisions`/`move_actor_towards_with_actor_collisions`; quando o alvo exato estiver bloqueado, o runtime consegue aproximar para o tile alcançavel mais proximo.
- Atores/NPCs solidos devem ser exportados com metadado de bloqueio suficiente para o template montar listas fixas de colisao ator-ator por frame; grupos 0-15 e `collision_mask` definem quem bloqueia quem. O Electron nao precisa acessar codigo privado, apenas gerar dados e usar as APIs publicas `*_with_actor_collisions`.
- Save data deve ser gerado como payload C++ pequeno e versionado, usando `gbs::SaveBank`/`gbs::SaveSlot` com assinatura unica por projeto; o Electron pode escolher quantidade/capacidade de slots, preencher `SaveMetadata` para titulo/tempo/room, usar `format_save_play_time` para labels e deve tratar mudancas de schema como nova versao de save ate existir migracao formal. O Electron pode declarar `topdown_project.save`, `platformer_project.save` ou `isometric_project.save` no manifesto de export para o `assetc` gerar `save_enabled` e `save_bank`; platformer/isometrico persistem `PlatformerSaveData`/`IsometricSaveData` diretamente em records SRAM, e o top-down habilita save/load manual conforme os slots exportados.
- HUD/menu simples pode ser exportado como texto estatico e `MenuItem[]`; menus maiores podem usar stack de telas, condicoes por variavel, toggle e slider sem heap. Layouts avancados com skins, icones ou grid livre devem continuar como dados do app ate haver template dedicado na engine.
- Debug/profile deve ser opcional no projeto exportado: o Electron pode gerar asserts, counters e overlay visual com `gbs/debug.hpp` para builds de smoke, sem depender de console, logs nativos ou codigo privado.
- Atualizacoes dinamicas de VRAM/paleta/OAM podem ser emitidas pelo template como fila DMA de VBlank; o Electron deve validar ou reportar excesso de updates por frame quando a fila fixa for insuficiente e pode usar `peak_queued` para avisar sobre cenas proximas do limite.
- Imagens bitmap exportadas podem escolher `assetc --bitmap-mode 3|4|5`, gerando headers C++ consumidos diretamente pelo runtime de render.
- Backgrounds affine exportados podem escolher `assetc --affine-tilemap`, gerando headers C++ 8bpp para BG2/BG3 consumidos diretamente pelo runtime de render.
- O Electron pode executar `assetc --pack-json` antes do build para obter um `GBAStudioAssetPackReport` com alocacoes, budgets, `budget_summary`, `production_summary`, `production_profile`, fingerprints por asset, status incremental, motivo de mudanca, validacao de ids unicos, uso por bancos/capacidade, uso por grupo, pressao por room/template, relatorios por pool, fragmentacao, overflow, recomendacoes de split, candidatos de compressao, fallback opcional, `export_plan` com headers/simbolos/argumentos do assetc e diagnosticos estruturados em formato JSON acionavel. Esse relatorio e contrato publico validavel por `engine_manifest.schemas.asset_pack_report` ou `gbsdoctor --validate-public-schema auto`.
- O Electron tambem pode executar `assetc --export-project-json` para materializar uma pasta exportada completa a partir de um manifesto: copia template, gera headers do `asset_pack`, grava `asset_pack_report.json` e escreve `gbastudio_project.json` pronto para `gbsdoctor`/`gbsbuild`.
- `diagnostics[]` deve ser tratado como superficie principal de UX: `warning` pode aparecer como aviso nao bloqueante, enquanto `error` bloqueia build/export. Codigos iniciais: `GBS_ASSET_PACK_BUDGET_NEAR_LIMIT` e `GBS_ASSET_PACK_RESOURCE_OVERFLOW`.
- Em builds incrementais, o Electron pode armazenar o ultimo relatorio e passar `--previous-pack-report`; `rebuild_plan.assets.skip` pode pular regeneracao/import caro, `rebuild_plan.assets.generate` deve ser regenerado, `rebuild_plan.assets.remove` informa quais caches locais devem ser invalidados e `export_plan.headers[].generate` entrega o mesmo plano ja associado ao header/simbolo final.
- Prioridades de BG e OBJ podem ser geradas como metadados estaticos de room/sprite sem exigir acesso ao codigo privado da engine.
- Spritesheets v0.5 tambem sao gerados como headers C++ pelo `assetc`, mantendo o Electron como orquestrador de processos.
- Arquivos gerados devem ficar dentro do diretorio do projeto exportado ou de um build dir informado pelo app.

## Plataformas

- macOS: usar devkitPro/devkitARM local ou empacotado pelo instalador.
- Windows: usar devkitPro/devkitARM para Windows, preferencialmente via ambiente MSYS2/devkitPro, mantendo suporte a caminhos com drive quando invocado pelo Electron.
- Linux: usar devkitPro/devkitARM instalado no sistema ou distribuido pelo instalador.

## Regras De Tooling

- Scripts novos devem evitar shell-specific behavior quando puderem ser CLIs em Python ou Node.
- Makefiles distribuidos podem assumir `make` e shell compativel com devkitPro/MSYS2, mas nao podem assumir recursos exclusivos do macOS.
- Separadores de caminho devem ser tratados pelo app chamador; o Engine Pack deve aceitar caminhos absolutos entre aspas.
- O `assetc` deve permanecer deterministico: mesmos inputs e flags geram o mesmo header em todas as plataformas.
- O `gbsbuild` deve suportar `--dry-run --json` para o app inspecionar a chamada antes de executar.
- O `gbsdoctor` deve retornar exit code diferente de zero quando checks obrigatorios falharem e JSON com lista de checks.
- O `gbsdoctor --json` deve expor plataforma, Python, separadores de path, variaveis relevantes, resumo do Engine Pack em `engine_manifest` e candidatos de executavel, incluindo `.exe` no Windows/MSYS2.
- O `gbsdoctor --json` deve expor `diagnostics` com generos, templates SDK, asset banking, render cost, audio cost, stress readiness, `resource_pool_readiness`, `butano_replacement_readiness`, toolchain e `actionable_messages[]`; o Electron deve preferir essas mensagens para orientar o usuario antes de iniciar build/export.
- Para promocao de backend, o Electron/GBA Studio deve tratar `diagnostics.butano_replacement_readiness.stage == "beta_candidate"` como liberacao privada e exigir `ready_for_primary_backend == true` antes de remover Butano do rollback legado/manual.
- A UI deve ler `diagnostics.butano_replacement_readiness.missing_manual_gates[]` e `next_actions[]` para mostrar proximos passos de promocao sem duplicar a regra da engine.
- Para telas de Settings/Export que so precisam do estado de promocao, prefira `gbsdoctor --readiness-only --json`; isso evita carregar/parsing do relatorio completo quando o app so quer mostrar beta/principal/bloqueios.
- Antes de qualquer release que tente tornar `gbastudio_engine` publicamente principal, o CI/app deve rodar `gbsdoctor --require-primary-ready --json`; exit code diferente de zero significa manter a maturacao privada e deixar Butano apenas como rollback legado/manual.
- Para logs de CI ou diagnostico exportavel, gere tambem `gbsdoctor --write-readiness-report readiness_decision.json --json`; esse artefato registra a decisao de promocao sem depender do relatorio completo e pode ser validado com `engine_manifest.schemas.readiness_report` ou diretamente por `gbsdoctor --validate-readiness-report readiness_decision.json --json`. Para anexar tudo em uma pasta de release, use `gbsdoctor --write-promotion-bundle promotion_bundle --json`; o bundle inclui `gbsdoctor_report.json` com checks, diagnostics, manifest completo, `public_schema_catalog.json` com os contratos publicos auditados, `promotion_summary.json` com um resumo compacto pronto para UI/CI e `file_integrity` com SHA-256 dos artefatos internos. Quando a chamada tambem passar `--readiness-evidence`, o bundle inclui a evidencia real validada como `readiness_evidence.json`. Valide depois com `gbsdoctor --validate-promotion-bundle promotion_bundle --json`; a resposta segue `engine_manifest.schemas.promotion_bundle_validation` e traz `readiness_summary`, `public_schema_catalog_summary` e `promotion_summary_summary` para UI/CI exibir gates faltantes, quantidade de schemas e pendencias sem parsear arquivos internos. Em CI/release de backend principal, use tambem `--require-primary-ready` para falhar enquanto o bundle arquivado ainda estiver em beta. Para conferir artefatos publicos por uma unica interface, use `gbsdoctor --validate-public-schema auto --schema-document <arquivo> --json`; isso evita que Electron replique validadores de `gbastudio_project`, `export_project`, `asset_pack`, `asset_pack_report`, `readiness_evidence`, `readiness_report`, `promotion_bundle`, `promotion_bundle_validation`, `promotion_summary` ou `public_schema_catalog`. Para montar formularios/validadores dinamicos, use `gbsdoctor --list-public-schemas --json` e leia `accepted_schema_arguments`, `sha256` e `missing_schemas`; se quiser arquivar esse catalogo, use `--write-public-schema-catalog` e valide-o depois com `--validate-public-schema public_schema_catalog`; se quiser conferir integridade contra o pacote atual, use `--verify-public-schema-catalog`.
- Quando houver evidencia externa, o app/CI deve validar `readiness_evidence.json` com `engine_manifest.schemas.readiness_evidence` e entao chamar `gbsdoctor --readiness-evidence readiness_evidence.json --json`; os campos aceitos sao `manual_mgba_stress_smoke`, `hardware_or_ci_validation` e `gba_studio_engine_primary_rollout`. Gates `ok: true` devem trazer `evidence_type`, `source` e `checked_at`; `cross_platform_ci` tambem deve trazer `validated_platforms`.
- Se a evidencia estiver incompleta, sem proveniencia ou tiver gates desconhecidos, `gbsdoctor` retorna checks `readiness_evidence_gate`, `readiness_evidence_gate_shape`, `readiness_evidence_gate_provenance` ou `readiness_evidence_extra_gate`; a UI deve tratar isso como bloqueio de promocao, nao como erro de build da ROM.
- Depois de uma confirmacao visual real das stress ROMs no mGBA, a UI/CI pode chamar `scripts/smoke_mgba.sh --stress --manual-pass --write-readiness-evidence readiness_evidence.json`; esse caminho marca apenas `manual_mgba_stress_smoke` e deixa hardware/CI e rollout privado da engine primaria pendentes para impedir promocao principal automatica.
- Depois de uma execucao real em CI ou hardware validado, a UI/CI pode chamar `tools/verify_cross_platform --hardware-ci-pass --write-readiness-evidence readiness_evidence.json`; esse caminho marca apenas `hardware_or_ci_validation`, exige execucao verde e deixa smoke mGBA e rollout privado da engine primaria pendentes.
- Em maquinas locais de desenvolvimento, `make verify-cross-platform-local` pode arquivar `local_cross_platform_dry_run`; a UI deve mostrar isso como evidencia diagnostica da plataforma atual, sem liberar `primary_ready` nem remover o rollback legado/manual.
- Depois de um rollout privado da engine primaria/export smoke validado com rollback legado preservado, a UI/CI pode chamar `tools/production_smoke --engine-primary-rollout-pass --write-readiness-evidence readiness_evidence.json`; esse caminho marca apenas `gba_studio_engine_primary_rollout`, exige smoke verde e deixa smoke mGBA e hardware/CI pendentes.
- Para criar a primeira versao do arquivo, a UI/CI pode chamar `gbsdoctor --print-readiness-evidence-template` e entao salvar/preencher o resultado, ou usar `gbsdoctor --write-readiness-evidence-template readiness_evidence.json --json` para deixar a propria CLI criar o arquivo.
- Para registrar evidencias reais sem duplicar a regra de schema no app, a UI/CI pode chamar `gbsdoctor --update-readiness-evidence readiness_evidence.json --readiness-gate <gate> --readiness-gate-ok true --readiness-gate-evidence-type <tipo> --readiness-gate-source <origem> --readiness-gate-checked-at <timestamp> --json`.
- Para combinar evidencias parciais sem editar JSON no app, a UI/CI pode chamar `gbsdoctor --merge-readiness-evidence readiness_evidence.json --readiness-evidence-input <parcial.json> ... --json`; a CLI valida cada entrada e promove apenas gates `ok=true`.
- O `verify_cross_platform` empacotado deve ser usado em CI ou maquinas reais para marcar macOS, Windows e Linux como validados sem inferir suporte apenas por manifestos.
- `engine_manifest.sdk_templates` deve alimentar a UI de criacao/exportacao de projetos por genero, incluindo features requeridas por template.
- Quando `gbastudio_project.json` existir, o `gbsdoctor --json` deve validar backend, entrada, dados do projeto, assets gerados e requisitos `requires.engine_pack`/`requires.features` antes do build.
- Features exigidas pelo projeto e ausentes no Engine Pack devem virar checks falhos no JSON para o Electron apresentar uma mensagem acionavel.
- Para distribuicao final, considerar empacotar `assetc` como binario por plataforma ou reimplementar o pipeline em Node/TypeScript se isso simplificar a integracao Electron.

## Validacao Minima Futura

- Build externo usando somente `GBAStudioEnginePack` em macOS, Windows e Linux.
- Execucao do `assetc` via processo externo com caminhos absolutos e diretorios temporarios.
- Execucao de `assetc --pack-json` como pre-flight de export/build, com `--previous-pack-report` quando houver cache, exibindo warnings de `diagnostics[]` e tratando exit code diferente de zero como erro de recursos exibivel ao usuario.
- Execucao de `assetc --export-project-json` para gerar uma pasta externa validavel com `gbastudio_project.json`, assets gerados e report de packing.
- Leitura de `export_plan.headers[]` para gerar/pular/remover headers de assets sem heuristicas de nome no app.
- Execucao de `gbsdoctor --json` com candidatos `.exe` em Windows/MSYS2 e sem extensao em macOS/Linux.
- Execucao de `tools/production_smoke --json` cobrindo top-down, platformer, isometrico e projeto exportado por `assetc --export-project-json`.
- Execucao de `tools/verify_cross_platform` em macOS, Windows e Linux reais, guardando o JSON de resultado por plataforma.
- Descoberta de `engine_manifest.sdk_templates` e validacao de que cada template apontado existe dentro do Engine Pack.
- Geracao de ROM `.gba` por projeto exportado sem dependencias do repo privado.
- Smoke no mGBA ou em emulador configurado pelo usuario.
