# Contrato Futuro de Integracao com GBA Studio

Este contrato descreve o formato que o exportador do GBA Studio deve gerar quando o backend `gbastudio_engine` for adicionado no futuro.

Ver tambem `docs/GBA_STUDIO_APP_AUDIT.md`, que registra a auditoria do app em 2026-06-02 e as lacunas entre os modelos atuais do GBA Studio e o contrato publico da engine.

## Entrada esperada pelo Engine Pack

Um projeto exportado deve conter:

- `main.cpp`: entrada do jogo com `extern "C" int gbs_main()`.
- `gbastudio_project_data.hpp`: dados estaticos de rooms, atores, portais, tilemaps, colisao, camera e assets.
- Assets compilados por `assetc` em headers C++ ou objetos linkaveis.
- `gbastudio_project.json`: manifesto simples do export contendo backend, tipo do projeto, entrada, dados gerados e features requeridas.
- `gbastudio_project.json.build`: configuracao opcional de build com `target` e `make_target`.
- Makefile baseado em `templates/Makefile.gba`.
- Em app Electron, caminhos de projeto, pacote e build devem ser passados por argumentos ou variaveis de ambiente, sem assumir layout de macOS.
- O caminho recomendado para build em app desktop e chamar `tools/gbsbuild` do Engine Pack.
- O caminho recomendado para diagnostico pre-build e chamar `tools/gbsdoctor` e ler o JSON retornado.
- O caminho recomendado para smoke automatizado de pacote/export e chamar `tools/production_smoke --json`.
- Antes de expor `gbastudio_engine` como backend beta no GBA Studio, chamar tambem `tools/stress_projects --json` e exigir `ok: true`.

## API publica inicial

- `gbs/engine.hpp`: inicializacao, VBlank, frame counter e cor de fundo.
- `gbs/dma.hpp`: copias DMA 16/32-bit com validacao de canal e tamanho.
- `gbs/timer.hpp`: timers de hardware basicos para contagem/reload.
- `gbs/interrupt.hpp`: callbacks configuraveis de VBlank, keypad e fontes de timer, com dispatch por bits reais de hardware no GBA.
- `gbs/input.hpp`: estado de botoes GBA.
- `gbs/render.hpp`: BG0-BG3, controle de modo 0/1/2/3/4/5, affine BG2/BG3 com mapas 8bpp, bitmap modes 3/4/5, prioridades BG/OBJ, sprites, metasprites, tilemaps ate 64x64, scroll por camada, parallax por background, blending, mosaic com enable por BG/OBJ, window0/window1, OBJ window, estimativa de custo de bitmaps e aplicacao de transformacoes affine por frame.
- `gbs/math.hpp`: `Fixed` Q8.8 saturado, trigonometria por LUT, `atan2`, raiz quadrada inteira, construcao de matrizes affine na convencao do GBA e amostragem sem ponto flutuante de keyframes de matrizes e anchors com `Easing`.
- `gbs/assets.hpp`: contratos de paleta, tiles 4bpp/affine 8bpp, tilemap, affine tilemap, metasprite e `RenderAssetCost` usados por `assetc`, templates e exportadores.
- `gbs/resource_manager.hpp`: managers estaticos para reservar tiles BG/OBJ, paletas e OAM com falha segura, batch transacional de assets, bancos fixos/automaticos, streaming de grupos com upload automatico por DMA de VBlank, relatorios de uso/fragmentacao, snapshots e rollback sem heap.
- `gbs/compression.hpp`: RLE 16-bit, LZ77 e Huffman estilo GBA para tilemaps, tiles 4bpp/OBJ 8bpp, paletas e dados estaticos sem heap. Para formatos compativeis com a BIOS, `gbs/bios.hpp` expoe `DivArm`, `IntrWait`, `BiosChecksum`, `SoundBiasChange`, `BitUnPack`, `LZ77UnComp`, `HuffUnComp`, `RLUnComp` e `Diff8/16bitUnFilter` com validacao de tamanho/alinhamento e fallback host; resets, SoundDriver e MultiBoot continuam fora do contrato seguro.
- `gbs/animation.hpp`: estado e avanco de animacoes de sprites.
- `gbs/audio.hpp`: SFX PSG, musica simples por steps, tracker PSG por patterns/order com `pan` discreto por rota esquerda/direita, PCM 8-bit assinado por Direct Sound, mixer PCM multi-voz, streaming PCM por blocos, controle de playback e `AudioMixCost` para diagnostico de assets/vozes.
- `gbs/project.hpp`: contrato data-driven de projeto top-down exportavel.
- `gbs/topdown.hpp`: room, player, camera, colisao, efeitos de tile e portais.
- `gbs/event.hpp`: bytecode de eventos com variaveis, branches simples, `EventRunner` progressivo e fila fixa de scripts com prioridade/cancelamento para `wait` real.
- `gbs/dialogue.hpp`: tabela de textos, estado de dialogo, caixa visual simples e paginacao automatica.

## Asset Pipeline

O exportador futuro deve chamar `assetc` para gerar headers C++ com:

- `PaletteAsset` com `start_index` alinhado ao banco de paleta escolhido.
- `TileAsset` com `destination_tile` e flag de tiles BG/OBJ.
- `TileMapAsset` com entradas ja ajustadas para `destination_tile` e `palette_bank`.
- `Rle16TileMapAsset` opcional para tilemaps repetitivos via `assetc --rle-tilemap`, quando o exportador quiser reduzir dados estaticos antes do load em VRAM.
- `Lz77TileMapAsset` opcional para tilemaps repetitivos via `assetc --lz77-tilemap`, quando o exportador quiser compressao local mais geral antes do load em VRAM.
- `Lz77TileAsset` opcional para tiles 4bpp ou OBJ 8bpp via `assetc --lz77-tiles`, mantendo o `TileAsset` bruto no mesmo header para compatibilidade com templates que ainda carregam tiles sem compressao. Dados LZ77 emitidos pelo `assetc` sao alinhados a 4 bytes para eventual uso de `LZ77UnCompWRAM`.
- `Lz77PaletteAsset` opcional para paletas via `assetc --lz77-palette`, mantendo o `PaletteAsset` bruto no mesmo header para compatibilidade com templates que ainda carregam paletas sem compressao.
- `HuffmanTileMapAsset`, `HuffmanTileAsset` e `HuffmanPaletteAsset` opcionais via `assetc --huffman-tilemap`, `assetc --huffman-tiles` e `assetc --huffman-palette`, mantendo os assets brutos no mesmo header. O encoder emite o cabecalho Huffman BIOS `0x20`, arvore e bitstream alinhados a 4 bytes; o runtime tenta `HuffUnComp` no GBA e usa decoder host sem heap fora do hardware.
- Recursos tipados de cena podem declarar `compression: "auto"` ou uma política manual `{ "strategy": "manual", "tiles": "huffman", "tilemap": "lz77", "palette": "none" }`. O Electron normaliza strings legadas, valida combinações incompatíveis e propaga a política para o asset pack; no modo automático o `assetc` compara as saídas compatíveis por componente. Os headers continuam contendo o asset bruto para os templates existentes, portanto o runtime/exportador deve selecionar explicitamente o membro comprimido quando carregar o recurso.
- `Bitmap16Asset`/`Bitmap8Asset` para modos 3/4/5 via `assetc --bitmap-mode 3|4|5`.
- `AffineTileAsset`/`AffineTileMapAsset` para BG2/BG3 via `assetc --affine-tilemap`; imagens devem gerar mapas quadrados de 16x16, 32x32, 64x64 ou 128x128 tiles.
- Resource managers podem reservar/liberar ranges de tiles, paletas e OAM, incluindo reservas diretas por `TileAsset` e `PaletteAsset`. `find_next_resource_range` permite prever o proximo range alinhado sem mutar o pool antes de decidir reservar. Para carregar uma room/export em lote, templates devem preferir `reserve_resource_batch`, que reserva tiles, paletas e OAM de forma transacional e restaura o snapshot anterior se qualquer item falhar. Para bancos maiores, `ResourceBank` permite reservar pools por tipo (`BgTiles`, `ObjTiles`, `BgPalette`, `ObjPalette`, `OamSprites`) com posicao fixa ou `start = 0xFFFF` para alocacao automatica alinhada; `preview_resource_bank_reservation` valida um banco sem mutar o manager, `preview_resource_banks` valida um lote transacional em um probe local, `preview_resource_bank_group` valida um grupo nomeado sem mutar o manager e preserva `group_name` no resultado, e `reserve_resource_banks`/`release_resource_banks` aplicam rollback transacional real. `ResourceBankGroup` agrupa bancos por room/area/cena, e `reserve_resource_bank_group`, `release_resource_bank_group`, `hot_swap_resource_bank_group` e `stream_resource_bank_group` preservam o nome do grupo ativo para streaming sem heap. Para escopos locais, `ResourceBankLease` e `ResourceBankGroupLease` liberam automaticamente as reservas no fim do escopo e aceitam somente buffers estaticos/do chamador, sem alocacao dinamica. Quando o exportador gerar `ResourceBankUploadSource[]`, templates devem preferir `stream_resource_bank_group_with_uploads`: ele troca o grupo, agenda uploads por DMA de VBlank, rejeita fonte ausente/fila cheia antes de mutar reservas e retorna `ResourceStreamResult` com status, banco afetado e uso/fragmentacao do pool para diagnostico exibivel. Para descarregar a mesma room/export, templates devem chamar `release_resource_batch`, `release_resource_banks` ou `release_resource_bank_group` com a reserva original; a engine limpa reservas apos sucesso e restaura snapshot se algum range estiver inconsistente.
- `GBAStudioAssetPackReport` via `assetc --pack-json`, recomendado como pre-flight antes de emitir headers finais; o JSON mede PNGs reais, exige `asset.id` unico quando informado, aplica `placement.start`/`placement.alignment`, emite budgets, `budget_summary`, `production_summary`, `asset_reports`, `pool_reports`, `diagnostics[]` com severidade/codigo estavel, fingerprints, status incremental, motivo de mudanca por asset, uso por bancos, uso por grupo, pressao por room/template, fragmentacao, `overflow_report`, `split_recommendations`, `compression_candidates`, `fallback_applied`, `export_plan` com headers/simbolos/argumentos sugeridos e reporta overflow de tiles, paletas, OAM ou PCM com `ok: false` para assets obrigatorios.
- `RenderAssetCost` e `AudioMixCost` devem ser usados pelos templates/exportadores para smoke de producao: eles estimam custos de render/audio em C++ puro antes de carregar VRAM, OAM ou iniciar playback, permitindo asserts de projeto exportado e counters de debug sem depender de codigo privado.
- O exportador deve tratar `diagnostics[].severity == "warning"` como aviso exibivel e `severity == "error"` como bloqueio de build. Codigos iniciais: `GBS_ASSET_PACK_BUDGET_NEAR_LIMIT` e `GBS_ASSET_PACK_RESOURCE_OVERFLOW`.
- Para import/build incremental, o exportador pode passar `--previous-pack-report previous.json`; o novo relatorio marca cada asset como `new`, `changed` ou `unchanged` em `allocations[].status`, explica a diferenca em `allocations[].change_reason`, lista removidos em `incremental.assets.removed` e oferece `rebuild_plan.assets.generate/skip/remove` e `export_plan.headers[].generate` como plano direto para cache e regeneracao.
- Collision flags por tile via `assetc --collision-color-index N`, gerando `*_collision_flags` e `gbs::TileMap`.
- Slope maps por tile via `assetc --slope-color-indexes A,B,C,D`, gerando `*_slope_tiles` para `BlockAboveRising`, `BlockBelowRising`, `BlockAboveFalling` e `BlockBelowFalling`.
- Tilemaps text/tiled em `32x32`, `64x32`, `32x64` ou `64x64`; a engine escolhe o tamanho de BG automaticamente por dimensao.
- Spritesheets nos 12 formatos OBJ nativos do GBA entre `8x8` e `64x64`, emitidas como um OBJ por frame com `SpriteAnimation` quando `--sprite-width`/`--sprite-height` forem informados. `--sprite-bpp 4|8` seleciona a profundidade; em 8bpp o `destination_tile` precisa ser par, cada tile logico consome 64 bytes e dois indices fisicos, e a paleta deve usar o banco OBJ global 0. Dimensoes fora desses pares exigem decomposicao explicita em metasprite.
- Audio PSG/tracker/PCM via JSON pequeno usando `assetc --audio-json`, gerando `SfxAsset`, `MusicAsset`, `TrackerAsset` e `PcmAsset`. `tracker[].mod` pode importar MOD ProTracker 4 canais subset para `TrackerAsset`, incluindo volume/finetune de sample, `0xy` arpeggio, `1xx`/`2xx` slides aproximados, `3xx` portamento aproximado, `4xy` vibrato aproximado, `7xy` tremolo aproximado, `Bxx` pattern jump, `Dxx` pattern break e efeitos basicos `Axy`/`Cxx`/`Fxx`, com `Fxx > 32` como BPM aproximado; `tracker[].s3m` pode importar S3M subset com notas, order table, volume de instrumento, volume column, `Axx`, `Bxx` pattern jump, `Cxx` pattern break, `Txx`, `Dxy`, slides aproximados `Exx`/`Fxx`, `Gxx` portamento aproximado, `Hxy` vibrato aproximado e `Rxy` tremolo aproximado; `tracker[].vgm` pode importar VGM SN76489 subset com writes PSG, waits basicos, mudancas de volume e noise channel, pulando Game Gear stereo byte e data blocks auxiliares. PCM Direct Sound continua assinado em 8 bits e `PcmSfxOptions::pan` distribui SFX entre FIFO A/B.
- Instrumentos WAV do piano roll usam `tracker[].samples[]` (`asset_id`, `wav`, `loop`) e steps com `sample_index`, `sample_pitch_ratio` e `sample_only: true`. O sample toca no mixer PCM sem duplicar a nota em PSG; a nota original do WAV determina a transposição. A exportação exige a capability `audio.tracker_sample_instruments`. Samples precisam conter 1 a 65.535 amostras após conversão; WAVs longos são rejeitados.
- No GBA, o relógio de áudio avança em VBlank independentemente dos frames de renderização. O mixer produz 528 amostras por frame a aproximadamente 31.536 Hz (timer de 532 ciclos), publica o bloco anterior antes de preparar o próximo e usa FIFO DMA com repetição. Mutações do playback são publicadas em seções críticas curtas; validação dos assets ocorre fora delas. `audio_update()` continua avançando um frame nos testes host.
- WAV PCM mono/stereo 8/16-bit pode ser referenciado por `pcm[].wav` relativo ao JSON exportado. Samples MOD ProTracker podem ser extraidos para `PcmAsset` com `pcm[].mod_sample` e `sample_index`; samples S3M 8/16-bit mono/stereo nao comprimidos podem ser extraidos com `pcm[].s3m_sample` e `instrument_index`, com downmix stereo para mono. `pcm[].loop_start_sample` e `pcm[].loop_end_sample` podem ser declarados pelo exportador; quando omitidos, loops nativos de samples MOD/S3M sao preservados automaticamente.

O `gbastudio_project.json` pode declarar `requires.engine_pack` e `requires.features`. O `gbsdoctor` compara esses requisitos com a versao e as capacidades do `enginepack.json`, permitindo que o app mostre erro de compatibilidade antes de chamar o build.

O `gbsdoctor --json` tambem retorna `engine_manifest`, um resumo pronto do `enginepack.json` com schema, nome, versao, grupos de capacidades, capacidades achatadas, contagem, ferramentas, schemas, templates e `sdk_templates`. O bloco `diagnostics` resume generos, templates SDK, asset banking, render cost, audio cost, stress readiness, `resource_pool_readiness`, `butano_replacement_readiness`, toolchain e `actionable_messages[]` com codigo/severidade/acao. O Electron deve preferir esses blocos para descoberta/compatibilidade em vez de reimplementar parsing do manifest.

`diagnostics.butano_replacement_readiness` e o contrato de promocao do backend proprio. O app pode mostrar `stage == "beta_candidate"` como backend beta selecionavel, mas so deve tornar `gbastudio_engine` principal quando `ready_for_primary_backend == true` e todos os itens de `required_before_primary_backend` tiverem evidencia externa registrada.
Para orientar a UI, o mesmo bloco expoe `missing_manual_gates[]` e `next_actions[]`; o app deve preferir essas mensagens/comandos sugeridos em vez de reconstruir a logica de promocao.
Quando a tela precisar apenas desse contrato, chame `gbsdoctor --readiness-only --json`; o formato retorna `kind: "butano_replacement_readiness"` e o bloco `butano_replacement_readiness` sem o restante dos checks.
Para automacao que precisa bloquear a promocao para backend principal, chame `gbsdoctor --require-primary-ready --json`; enquanto `ready_for_primary_backend` for falso, a CLI retorna codigo diferente de zero e ainda imprime o contrato compacto.
Para arquivar a decisao de promocao como evidencia de release, chame `gbsdoctor --write-readiness-report readiness_decision.json --json`; esse arquivo usa o mesmo formato compacto de `--readiness-only` e pode ser validado depois com `gbsdoctor --validate-readiness-report readiness_decision.json --json`. Para release/CI, `gbsdoctor --write-promotion-bundle promotion_bundle --json` cria a decisao, validacao, template de evidencias, catalogo publico de schemas, resumo legivel, `promotion_summary.json` compacto para UI/CI, `gbsdoctor_report.json` completo e hashes SHA-256 em `file_integrity` em uma pasta previsivel; quando `--readiness-evidence` for fornecido, o mesmo bundle inclui o `readiness_evidence.json` real validado e seu hash. `gbsdoctor --validate-promotion-bundle promotion_bundle --json` valida o manifest, arquivos declarados, catalogo publico e integridade dos artefatos internos e retorna `readiness_summary`, `public_schema_catalog_summary` e `promotion_summary_summary` para UI/CI conforme `engine_manifest.schemas.promotion_bundle_validation`. Para promover a engine como backend principal usando um bundle arquivado, rode `gbsdoctor --validate-promotion-bundle promotion_bundle --require-primary-ready --json`. Para uma validacao uniforme de contratos publicos, o app/CI pode chamar `gbsdoctor --validate-public-schema auto --schema-document artifact.json --json`; quando preferir ser explicito, troque `auto` por `gbastudio_project`, `export_project`, `asset_pack`, `asset_pack_report`, `readiness_evidence`, `readiness_report`, `promotion_bundle`, `promotion_bundle_validation`, `promotion_summary` ou `public_schema_catalog`. Para descoberta de UI/CI, `gbsdoctor --list-public-schemas --json` retorna todos os IDs aceitos, caminhos, existencia, tamanho, SHA-256 e schemas ausentes no Engine Pack; `gbsdoctor --write-public-schema-catalog public_schema_catalog.json --json` grava o mesmo catalogo como artefato validavel; `gbsdoctor --verify-public-schema-catalog public_schema_catalog.json --json` compara o artefato arquivado contra o pacote atual.

Para anexar evidencia, chame `gbsdoctor --readiness-evidence readiness_evidence.json --json` ou defina `GBS_READINESS_EVIDENCE`. O app pode validar o arquivo antes usando `engine_manifest.schemas.readiness_evidence`. O JSON minimo esperado e:

```json
{
  "manual_mgba_stress_smoke": { "ok": true, "evidence_type": "manual_mgba_stress_smoke", "source": "mGBA smoke log", "checked_at": "2026-06-11T13:00:00Z" },
  "hardware_or_ci_validation": { "ok": true, "evidence_type": "cross_platform_ci", "source": "CI run", "checked_at": "2026-06-11T13:10:00Z", "validated_platforms": ["macos", "windows", "linux"] },
  "gba_studio_engine_primary_rollout": { "ok": true, "evidence_type": "gba_studio_engine_primary_rollout", "source": "private engine-primary rollout smoke", "checked_at": "2026-06-11T13:20:00Z" }
}
```

Campo `message` e opcional e aparece em `manual_primary_gates[]`. Gates `ok: true` exigem `evidence_type`, `source` e `checked_at`; `local_cross_platform_dry_run` pode ser arquivado, mas nao libera `primary_ready`, e `cross_platform_ci` so libera quando `validated_platforms` contem `macos`, `windows` e `linux`.
O `gbsdoctor` tambem aplica validacao semantica equivalente ao schema: os tres gates sao obrigatorios, cada gate deve ser booleano ou objeto com `ok` booleano, gates desconhecidos bloqueiam a promocao e proveniencia ausente gera `readiness_evidence_gate_provenance`.
Quando a validacao manual das stress ROMs no mGBA for concluida, `scripts/smoke_mgba.sh --stress --manual-pass --write-readiness-evidence readiness_evidence.json` pode gerar a evidencia parcial de `manual_mgba_stress_smoke`; por contrato, esse caminho mantem `hardware_or_ci_validation` e `gba_studio_engine_primary_rollout` como pendentes ate que esses gates tenham evidencias proprias.
Quando a validacao em CI ou hardware real for concluida, `tools/verify_cross_platform --hardware-ci-pass --write-readiness-evidence readiness_evidence.json` pode gerar a evidencia parcial de `hardware_or_ci_validation`; por contrato, esse caminho exige execucao verde, nao aceita `--skip-toolchain` e mantem `manual_mgba_stress_smoke` e `gba_studio_engine_primary_rollout` pendentes.
Quando a validacao for apenas local, `make verify-cross-platform-local` gera `local_cross_platform_dry_run` para arquivo e diagnostico. Esse tipo deve continuar bloqueado por `gbsdoctor --require-primary-ready` ate existir evidencia real de CI/hardware cobrindo macOS, Windows e Linux.
Quando o rollout privado da engine primaria/export smoke com rollback legado preservado for concluido, `tools/production_smoke --engine-primary-rollout-pass --write-readiness-evidence readiness_evidence.json` pode gerar a evidencia parcial de `gba_studio_engine_primary_rollout`; por contrato, esse caminho exige smoke verde, nao aceita `--skip-build` e mantem `manual_mgba_stress_smoke` e `hardware_or_ci_validation` pendentes.
Para iniciar um arquivo sem duplicar estrutura no app, use `gbsdoctor --print-readiness-evidence-template` ou `gbsdoctor --write-readiness-evidence-template readiness_evidence.json --json`. Para preencher gates sem mutar JSON no app, use `gbsdoctor --update-readiness-evidence readiness_evidence.json --readiness-gate manual_mgba_stress_smoke --readiness-gate-ok true --readiness-gate-evidence-type manual_mgba_stress_smoke --readiness-gate-source "mGBA smoke log" --readiness-gate-checked-at "2026-06-11T13:00:00Z" --json`. Para juntar evidencias parciais criadas por ferramentas diferentes, use `gbsdoctor --merge-readiness-evidence readiness_evidence.json --readiness-evidence-input partial_mgba.json --readiness-evidence-input partial_ci.json --readiness-evidence-input partial_rollout.json --json` antes de chamar `--readiness-evidence`.

Para selecionar tipo de projeto, o app deve ler `engine_manifest.sdk_templates`. A versao 1.0 declara `topdown_basic`, `platformer_basic` e `isometric_basic`; templates futuros devem entrar nesse catalogo antes de aparecerem na UI.

## Projeto Top-down Data-driven

O exportador futuro deve usar `RoomRuntimeSpec` como representacao intermediaria normalizada do app sempre que possivel. Esse spec ja agrega rooms, atores, triggers, player spawn, scripts, camera, parallax, colisao e audio por room. O backend `gbastudio_engine` deve transformar esse spec em `gbastudio_project_data.hpp`, em vez de depender diretamente de detalhes internos de UI ou preview.

O header `gbastudio_project_data.hpp` deve expor um `const gbs::TopDownProjectData project` com:

- paletas, tiles e backgrounds carregaveis pela API publica;
- backgrounds com tilemap direto ou `compressed_tilemap`, scroll inicial e fatores de parallax 8.8;
- bancos planejados em `topdown_project.resource_banks`, usando `kind`, `start` fixo ou `"auto"`, `count`, `alignment` e `name`, ou o atalho `"asset_pack"` para usar `asset_pack_report.resource_bank_plan`, para o template reservar recursos via `reserve_resource_banks` antes do load;
- rooms com visual tiles, colisao, tamanho, nome estavel opcional e portais;
- metadata opcional por room para camera, player start, musica e cor de fundo;
- hotspots retangulares opcionais de interacao por room;
- NPCs/atores opcionais por room com posicao, tamanho, metasprite, animacao, script de interacao e movimento opcional por dados;
- scripts opcionais de entrada/saida de room, portal, interacao e tabela de scripts nomeados para resolucao por ID estavel;
- tabela de textos para `show_dialogue`, com textos longos paginados automaticamente pela engine;
- grupos de escolha para `show_choice`, com opcoes estaticas, variavel de destino para o resultado e script opcional por opcao;
- tabela de `SfxAsset`, `MusicAsset`, `TrackerAsset` e `PcmAsset` para eventos, musica simples, tracker PSG e Direct Sound PCM;
- assets de sprite/metasprite gerados pelo `assetc` para player e NPCs;
- player inicial com posicao, tamanho, velocidade e metasprite;
- camera inicial e cor de fundo;
- layout opcional de save em SRAM usando `SaveSlot` fixo, assinatura de quatro bytes e versao por schema exportado.
- textos curtos opcionais para HUD/menu quando o template quiser expor UI nativa da engine.

Como primeira ponte automatica, `assetc --export-project-json` aceita `topdown_project` no manifesto de export. Esse bloco gera um `gbastudio_project_data.hpp` minimo com rooms, tilemap visual por byte, collision flags por byte, portais retangulares, metadata de room, NPCs/atores, triggers, choice groups, scripts simples de room/portal/interacao/NPC/trigger/escolha, player, camera e linhas simples de dialogo. Para projetos de plataforma, o mesmo comando aceita `platformer_project` e gera `platformer_project_data.hpp` com rooms, tilemap visual por byte, collision flags por byte, player start, camera, config fisica, hazards, checkpoints e camera zones. Para projetos isometricos, aceita `isometric_project` e gera `isometric_project_data.hpp` com rooms, grid, camera, collision flags e atores iniciais. Quando o manifesto contem `asset_pack`, `resource_banks` tambem pode ser a string `"asset_pack"` para materializar os bancos a partir das alocacoes automaticas do pack. Cada asset do pack pode declarar `bank_group` para que `asset_pack_report.resource_bank_groups[]` represente bancos por room, area ou conjunto compartilhado; a partir do Engine Pack v1.13, esses grupos tambem sao emitidos no header como `gbs::ResourceBankGroup`, expostos em `project.resource_bank_groups` e podem ser ligados diretamente a cada room. `assets.bg_palettes`, `assets.obj_palettes` e `assets.tile_assets` alimentam o projeto, e o top-down tambem aceita `sfx_assets`, `music_assets`, `pcm_assets` e `tracker_assets`. O Engine Pack publica `schemas/export_project.schema.json` para o Electron validar essa entrada antes de chamar `assetc`.

Eventos suportam `show_dialogue`, `show_dialogue_if`, `warp`, `set_variable`, `clear_variable`, `add_variable`, `jump`, branches por variavel igual/diferente, branch por flag setada e `play_sfx` audivel via PSG. O exportador deve gerar `EventCommand` estatico e referenciar textos/SFX por indice em `TopDownProjectData`. PCM 8-bit assinado ja pode ser declarado em `PcmAsset`; WAV PCM mono/stereo 8/16-bit, samples MOD via `pcm[].mod_sample` e samples S3M 8/16-bit mono/stereo via `pcm[].s3m_sample` podem ser importados por `assetc --audio-json`. Tracker PSG v1 pode ser gerado como `TrackerAsset`; MOD ProTracker 4 canais subset pode ser convertido via `tracker[].mod`, com volume/finetune de sample, `0xy`, `1xx`, `2xx`, `3xx`, `4xy`, `7xy`, `Axy`, `Bxx`, `Dxx`, `Cxx` e `Fxx`, incluindo BPM `Fxx > 32`; S3M subset pode ser convertido via `tracker[].s3m`, com notas, volume de instrumento, volume column, speed `Axx`, pattern jump `Bxx`, pattern break `Cxx`, tempo `Txx`, volume slide `Dxy`, slides aproximados `Exx`/`Fxx`, portamento `Gxx`, vibrato `Hxy` e tremolo `Rxy`; VGM SN76489 subset pode ser convertido via `tracker[].vgm`, com writes PSG, waits basicos, mudancas de volume, noise, stereo byte ignorado e data blocks pulados. Playback sincronizado de samples MOD/S3M, chips VGM avancados e efeitos finos ainda ficam fora desta fase.

Para casar com o app atual, o bytecode tambem aceita `show_choice`, `play_music`, `stop_music`, `close_dialogue`, `wait`, `set_camera_position`, `follow_camera`, `lock_camera`, `call_script` e comandos basicos de visibilidade/posicao/direcao/animacao de ator. `DialogueChoice::script_index` pode apontar para um script de `TopDownProjectData::scripts`; o template top-down grava o resultado da escolha e enfileira esse script apos o fechamento da caixa. `EventRunner` deve ser usado por templates que precisam de espera real entre comandos; `EventScriptQueue` encadeia scripts sem heap, como `on_exit -> portal -> on_enter`, e tambem permite enfileirar na frente, limpar pendencias e cancelar runner ativo. `run_event_script` continua disponivel para execucao instantanea e compatibilidade. A proxima revisao ainda deve cobrir comandos complexos de ator e selecao por nome/ID estavel. Comandos tipados do app fora dessa subset devem aparecer no relatorio de export como `previewOnly`, `stub` ou `unsupported`.

Room streaming v0.6 usa `TopDownProjectData::rooms` como tabela estatica. Cada warp valida o indice de room, troca `Room` em memoria, reposiciona o player e executa `on_enter` da room destino quando o warp veio de script.

NPCs/atores v0.11 vivem dentro de cada `TopDownRoomData`. O runtime deve priorizar `npc_event_script_for` antes de hotspots retangulares e antes do fallback `on_interact`, permitindo que atores executem dialogo, variaveis e SFX sem codigo customizado por room. Rooms, NPCs e scripts tambem podem ser resolvidos por nome estavel com helpers publicos, o que permite ao exportador preservar IDs do app sem depender de busca manual por indice.

Room metadata v0.13 vive em cada `TopDownRoomData` e deve ser aplicada no boot e apos troca de room. Rooms simples podem usar `default_room_metadata()` para manter fallback de camera, backdrop e musica do projeto.

`TopDownRoomMetadata` carrega bounds de camera em pixels derivados de `CameraBoundsSettings`. `TopDownNpcData`/actor data preserva nome, direcao, collision group, movement speed x100, animation speed percent e scripts por slot (`onStart`, `onUpdate`, `onHitActor`, `onHitPlayer`, grupos 1-3). IDs estaveis do app ainda devem ser mapeados pelo exportador em tabela propria ou nomes gerados.

`TopDownNpcMovementData` permite exportar movimento automatico simples sem codigo customizado: `None`, patrulha horizontal/vertical, wander em bounds, follow player e path-to-point. Follow/path usam BFS limitado a 64 tiles e sem heap; `find_actor_path_step_with_actor_collisions` tambem aceita listas fixas de atores bloqueadores e pode retornar o primeiro passo para o tile alcançavel mais proximo quando o alvo exato esta bloqueado. Projetos maiores devem escolher `max_search_tiles` conservador e reportar comportamentos de IA avancada como fora do subset atual.

`TopDownActorRuntime` representa o estado mutavel de NPCs/atores durante a execucao. O exportador pode gerar dados estaticos e deixar o template runtime aplicar comandos de evento como `set_actor_visible`, `set_actor_active`, `set_actor_position`, `move_actor`, `set_actor_direction`, `set_actor_speed` e `set_actor_animation`. Templates gerados devem preferir `consume_actor_event_commands` para aplicar a fila inteira e limpa-la de forma deterministica.

Actor Collision v0.81 usa listas fixas de `gbs::Actor` como bloqueadores para player e NPCs, filtradas por `collision_group` e `collision_mask`. O exportador deve marcar quais atores sao solidos, gerar grupos 0-15 e mascaras de bloqueio por ator, montar arrays temporarios pequenos no template e chamar `update_player_with_actor_collisions`, `move_actor_by_delta_with_actor_collisions` ou `move_actor_towards_with_actor_collisions`. A engine tambem expoe `actor_overlaps_actor`, `rect_hits_actor`, `rect_hits_any_actor` e `rect_hits_any_blocking_actor` para validacao de triggers e interacoes. Resolucao com push e prioridades dinamicas ainda ficam para template futuro.

Resource Managers v1.16 permitem que templates de streaming capturem snapshots antes de carregar assets de uma room/banco/grupo e revertam o manager se alguma reserva falhar. Exportadores devem preferir `reserve_resource_batch` para validar tiles, paletas e OAM de uma room/export antes do load, `reserve_resource_banks` quando a unidade de carga for um banco planejado pelo asset pack, `preview_resource_bank_group` para diagnosticar grupos de room antes do streaming, `reserve_resource_bank_group` quando a unidade for um grupo vindo de `ProjectData::resource_bank_groups`, `stream_resource_bank_group` quando o template mantiver um grupo ativo por room, `release_resource_batch`/`release_resource_banks`/`release_resource_bank_group` para descarregar o mesmo lote e `capture_resource_manager_snapshot`/`restore_resource_manager_snapshot` quando precisarem abortar um fluxo customizado sem deixar tiles, paletas ou OAM marcados de forma inconsistente. Templates podem localizar grupos por nome estavel com `find_*_resource_bank_group_index(project, name)` ou `resource_bank_group_from_*_project(project, name)`, e tambem podem resolver diretamente a partir da room com `find_*_room_resource_bank_group_index(project, room)` ou `resource_bank_group_from_*_room(project, room)`. Para streaming sob demanda, templates podem manter um `ResourceBankCache` estatico e chamar `reserve_resource_bank_cached`; a engine tenta reservar o banco, evicta candidatos desbloqueados de menor prioridade/uso mais antigo e restaura manager/cache se a reserva final falhar. A partir do Engine Pack v2.3, `resource_bank_cache_contains_group`, `promote_resource_bank_group_from_cache` e `hot_swap_resource_bank_group_from_cache` permitem transformar bancos prefetched em grupo ativo, transferindo a posse das reservas do cache para o runtime sem reservar nem copiar de novo. A partir do Engine Pack v2.4, os templates top-down, platformer e isometrico empacotados usam esse caminho automaticamente quando `ResourceBankUploadSource[]` existe: fazem prefetch periodico de grupos de outras rooms e, na troca de room, tentam promover o grupo antes de chamar o streaming/upload normal. A partir do Engine Pack v2.5, exportadores podem usar `ResourceBankPrefetchWindow` com `prefetch_resource_banks_for_camera_window` ou `prefetch_resource_banks_for_camera_window_with_uploads` para pular bancos fora da janela expandida de area/metatile antes de reservar VRAM ou exigir `ResourceBankUploadSource`. A partir do Engine Pack v2.6, `ResourceBankPrefetchPolicy` e as variantes `*_policy` limitam quantas reservas novas e quantos uploads podem ser feitos por chamada, mantendo reuso de bancos em cache e pulando o restante como trabalho de frames futuros. A partir do Engine Pack v2.7, os templates top-down, platformer e isometrico empacotados usam essa policy no prefetch periodico, com limite padrao de dois bancos novos/uploads por chamada para distribuir streaming entre frames. A partir do Engine Pack v2.8, `prune_resource_bank_cache` permite liberar preventivamente entradas antigas/despriorizadas por idade, prioridade e pool, sem tocar entradas travadas e com rollback em caso de falha. A partir do Engine Pack v2.9, `preview_resource_bank_cache_prune` retorna `ResourceBankCachePrunePreview` com entradas ativas, travadas, podaveis e unidades liberaveis sem mutar cache/VRAM, permitindo que exportadores e UI estimem impacto antes de aplicar poda real. `set_resource_bank_cache_locked` protege bancos criticos durante transicoes e `touch_resource_bank_cache_entry` atualiza recencia. Quando houver dados prontos para copiar, `resource_bank_upload_transfer`, `enqueue_resource_bank_upload_vblank`, `enqueue_resource_bank_uploads_vblank` e `enqueue_resource_bank_upload_sources_vblank` mapeiam reservas para VRAM/paleta/OAM e agendam transferencias na fila DMA de VBlank; `assetc --export-project-json` pode gerar `ResourceBankUploadSource[]` por nome de banco a partir do `asset_pack`, evitando C++ manual e dependencia da ordem das reservas. `capture_engine_resource_usage` pode alimentar overlays de smoke ou diagnosticos do template; `largest_free_block` mostra se um asset grande cabe em bloco contiguo e `free_block_count` mostra o nivel de fragmentacao mesmo quando ainda ha espaco total restante. Os templates top-down, platformer e isometrico empacotados agora usam `ProjectData::resource_bank_groups` para streamar o grupo da room inicial, do restore de save e das trocas de room; sem grupos, preservam `ProjectData::resource_banks` global e, sem esse bloco, o caminho antigo por `reserve_resource_batch`. Exportadores devem manter `tile_asset_count`, `bg_palette_count`, `obj_palette_count`, `resource_bank_count` e `resource_bank_group_count` dentro dos limites declarados pelo template ou gerar um template com limites maiores.

Platformer Runtime v1.9 usa `PlatformerProjectData` como contrato data-driven publico. Exportadores devem gerar `platformer_project_data.hpp` com um `const gbs::PlatformerProjectData project`, contendo paletas, tiles, tabela de rooms, room inicial e cor de fundo. O caminho alto nivel `platformer_project` em `assetc --export-project-json` ja cobre o subset essencial sem C++ manual. Cada `PlatformerRoomData` agrega tilemap visual, collision flags, tamanho, `Rect` inicial do player, camera inicial, `PlatformerConfig`, hazards, checkpoints, camera zones, enemies, moving platforms e scripts opcionais de `on_enter`, `on_exit`, `on_update`, hazard `on_hit`, checkpoint `on_activate`, camera zone `on_enter`, enemy `on_hit`/`on_touch`/`on_hit_player` e moving platform `on_stand`/`on_contact`/`on_ride`/`on_touch`. Tiles `TileSolid`, `TileBlockTop`, `TileLadder` e slopes `BlockBelowRising`/`BlockBelowFalling` viram chao/parede, plataforma one-way, escada e rampa 45 graus com `snap_platformer_actor_to_slope_floor`. Hazards retangulares podem causar dano, respawn e disparar script pelo indice atingido em `PlatformerRuntimeState::hazard_index`; checkpoints retangulares atualizam o respawn e disparam script pelo id; camera zones podem aplicar bounds/offset/lock X/Y por trecho e disparar script na entrada. Inimigos patrulheiros e moving platforms sao carregados por room em arrays fixos no template, sem heap; inimigos disparam scripts por indice atingido e plataformas moveis disparam scripts por indice quando carregam o player.

Isometric Runtime v1.13 usa `IsometricProjectData` como contrato data-driven publico. Exportadores devem gerar `isometric_project_data.hpp` com um `const gbs::IsometricProjectData project`, contendo paletas, tiles, tabela de rooms, room inicial e cor de fundo. O caminho alto nivel `isometric_project` em `assetc --export-project-json` ja cobre o subset essencial sem C++ manual. Cada `IsometricRoomData` agrega tilemap visual, collision flags, tamanho, atores iniciais, `IsoGridConfig`, camera inicial, `cursor_start` opcional e scripts opcionais de `on_enter`, `on_exit`, `on_update`, ator `on_interact`, `on_start`, `on_update` e tile `on_interact`/`on_select`/`on_activate`. Eventos de tile podem ser pontuais ou declarar `area`/`bounds` com `x`, `y`, `z`, `width` e `height`; o runtime usa `iso_tile_event_script_for` para resolver o script dentro da area. O template empacotado consome esse objeto diretamente e usa `iso_tilemap_from_room`, `IsoCursorState`, `iso_room_cursor_start`, `find_iso_actor_at_cursor`, `iso_cursor_actor_interact_event_script_for`, `consume_iso_actor_event_commands`, `build_iso_draw_list` e `sort_iso_draw_list` para selecao de tile, interacao com ator selecionado, aplicacao de comandos de evento e ordenacao de sprites por profundidade; scripts `warp` podem trocar de room e usar `x/y` como tile inicial do ator 0. O template tambem restaura o save mais recente no boot e autosalva `IsometricSaveData` apos interacao/warp, incluindo cursor selecionado quando o template passar o estado para os helpers de save. A API atual cobre grid/camera/ordenacao, picking por diamond mask, cursor/seleção por tile, cursor inicial por room, interação de ator pelo cursor, bloqueio por tile/ator, movimento validado, passo greedy, BFS limitado, A* limitado em direcao ao alvo, eventos por ator/tile/area e comandos basicos de evento para visibilidade/posicao de ator. Save System v0.89 usa SRAM 32 KB com `SaveBank` de slots fixos e records opcionais com `SaveMetadata`. O exportador deve gerar uma assinatura unica por jogo/projeto, uma versao de schema, quantidade/capacidade de slots e um payload estatico compacto; a engine valida assinatura, versao, tamanho e checksum antes de entregar bytes ao runtime. `gbs::configured_cartridge_save_capabilities()` publica a geometria e a disponibilidade do backend configurado: hoje `Sram32K` e o unico backend de runtime habilitado; Flash e EEPROM sao descritos como capacidades sem protocolo habilitado, e `detected_cartridge_save_device()` retorna `Unknown` ate existir um probe seguro por hardware. `save_backend_status()`/`configured_save_backend_status()` retornam `UnsupportedDevice` para dispositivos sem backend habilitado, e as operacoes de save nao fazem fallback por assinatura. Os builders `make_flash_program_sequence()`, `make_flash_sector_erase_sequence()`, `make_eeprom_read_frame()` e `make_eeprom_write_frame()` permitem testar a ordem de comandos e o framing MSB-first sem escrever em cartucho; eles nao habilitam suporte fisico. Isso evita inferir capacidade ou escrever em cartucho desconhecido. `format_save_play_time` formata `play_time_frames` como `MM:SS` ou `H:MM:SS` para labels sem heap. O template top-down atual salva room, posicao do player, variaveis, titulo de slot, tempo de jogo, room e flags em ate tres slots visiveis, restaura o save mais recente no boot, permite save/load manual no menu de pausa e usa `sequence` para ordenar progresso. Para platformer, isometrico e shmup, os headers publicos expoem `PlatformerSaveData`, `IsometricSaveData` e `ShmupSaveData` com helpers de captura/aplicacao para room ou wave, player/atores, camera quando aplicavel, score/high score, variaveis e tempo de jogo; `assetc --export-project-json` pode emitir o `save_bank` diretamente a partir de `project.save` em qualquer genero, e os templates consultam `save_enabled` antes de restaurar/autosalvar. Screenshots de save, nomes editaveis, migracao entre versoes e UI de load/save customizada ainda ficam para templates futuros.

UI v0.86 usa `gbs/ui.hpp` para HUD simples e `gbs/menu.hpp` para menu textual sem heap. O exportador pode mapear pausa, inventario simples ou opcoes para `MenuItem[]`, com stack de telas, itens habilitados/desabilitados, condicoes por variavel, itens escondidos quando indisponiveis, toggles, sliders e scripts por item. O template top-down atual usa Start para abrir PAUSE e acionar save/load manual multi-slot com labels derivadas da metadata de save. Skins, layout livre, icones, inventario complexo e telas dedicadas de load/save ainda ficam para templates futuros.

Debug/Profile v0.79 usa `gbs/debug.hpp` para asserts leves, budget por frame, counters nomeados e overlay visual opt-in. O exportador pode gerar asserts de pre-flight runtime para limites de room, recursos, atores e scripts, alem de counters para diagnostico consumivel em smoke manual. Templates podem chamar `debug_overlay_text` para integrar com UI propria ou `draw_debug_overlay` para desenhar a text box padrao da engine; o template top-down atual mostra o overlay ao segurar Select.

DMA VBlank Queue v0.84 permite que templates exportados agendem copias pequenas de VRAM/paleta/OAM com `dma_enqueue_vblank*` e deixem `wait_vblank` drenar a fila automaticamente no DMA channel 3. O exportador deve tratar overflow de fila como erro de build/smoke quando a quantidade de updates por frame passar de 8 ou dividir updates em frames diferentes. `dma_vblank_queue_stats().peak_queued` ajuda a diagnosticar cenas perto do limite, e `dma_reset_vblank_queue_stats` zera contadores sem descartar a fila. Copias criticas ainda podem usar `dma_copy16`/`dma_copy32` imediato quando o template controlar o timing.

Render Mosaic v0.78 separa o tamanho global do efeito (`set_mosaic`) do enable real por camada/sprite (`set_bg_mosaic` e `Sprite::mosaic`). Exportadores devem emitir o tamanho uma vez por tela/room e ligar o bit apenas nos BGs/OBJs que precisam do efeito; isso evita aplicar mosaic acidental em HUD, dialogos ou sprites de interface.

Triggers do app (`TriggerDocument`) viram dados separados de hotspot simples: area, script de entrada, script de saida, `runOnce`, cooldown, condicao reservada e tipo. A primeira versao pode compilar apenas triggers standard e reportar water/damage como efeito parcial quando a engine ainda so tratar colisao solida.

`CollisionPaintType` do app pode ser mapeado para flags da engine: `solid`, `top`, `bottom`, `left`, `right`, `water`, `damage` e `ladder`. A engine permite consultar `water`/`damage`/`ladder` sob um retangulo ou ator e tambem declarar `TopDownTileEffectEventData` por room para scripts de entrada/saida por mascara de efeito. Slopes podem ser exportados como tabela opcional `TileSlope` por room (`BlockAboveRising`, `BlockBelowRising`, `BlockAboveFalling`, `BlockBelowFalling`) e anexados ao `TileMap`/`TopDownRoomData::slope_tiles`; quando a fonte for PNG, o exportador pode chamar `assetc --slope-color-indexes A,B,C,D`.

Dialogos devem resolver `DialogueEntry.key` para indice em `DialogueLine`. Quando houver traducao ativa, o exportador escolhe o texto traduzido. Choices podem ser exportadas como `TopDownDialogueChoiceData`; a versao atual mostra duas opcoes por janela, rola grupos maiores e grava o resultado em variavel.

Audio deve resolver `AudioItem.name`/`exportID` para `SfxAsset`/`MusicAsset`/`TrackerAsset`/`PcmAsset`. Composicoes PSG simples, tracker PSG por patterns/order com `pan` opcional, MOD ProTracker 4 canais subset com volume/finetune de sample, `0xy`, `1xx`, `2xx`, `3xx`, `4xy`, `7xy`, `Axy`, `Bxx`, `Dxx`, `Cxx` e `Fxx`/BPM, S3M subset com volume de instrumento, volume column, `Axx`, `Bxx` pattern jump, `Cxx` pattern break, `Txx`, `Dxy`, `Exx`, `Fxx`, `Gxx`, `Hxy` e `Rxy`, VGM SN76489 subset com volume/noise e skips seguros para stereo/data blocks, PCM 8-bit assinado, WAV PCM mono/stereo 8/16-bit e samples MOD/S3M extraidos para PCM podem ser convertidos por `assetc --audio-json`; S3M stereo e downmixado para mono no asset pipeline. O `pan` do PSG seleciona discretamente a rota esquerda, direita ou ambas porque o hardware nao fornece ganho continuo por canal. Loops nativos de samples MOD/S3M sao preservados como loop points PCM, e o exportador pode sobrescrever esses pontos no JSON. SFX PCM podem ser exportados com prioridade/volume/pan; a engine mixa ate 4 SFX simultaneos com musica PCM em buffers estereo e envia FIFO A/B com panning. Modulos com playback sincronizado de samples/efeitos finos ou VGM com chips fora do subset devem ser reportados como fora do escopo ou convertidos previamente.

## Regras de integracao

- Nao incluir headers privados de `engine/src`.
- Nao depender de Butano ou `libgba`.
- Linkar somente contra `lib/libgbastudio_engine.a`.
- Consumir o Engine Pack por CLIs chamaveis via processo externo, compativel com Electron em macOS, Windows e Linux.
- Preferir `gbsbuild --engine-pack ... --project-dir ... --target ...` em vez de montar a chamada de `make` diretamente no app.
- Usar `gbsdoctor --json` para apresentar diagnosticos acionaveis ao usuario antes de builds.
- Usar o Exemplo GBA completo como gate principal de integracao: autoria no app,
  save/reopen, export mixed de todos os runtimes, build de uma ROM e Play Window.
- Usar `production_smoke --json` em CI/preflight para diagnosticar templates
  top-down, platformer, isometrico e projeto gerado por
  `assetc --export-project-json` quando o gate completo falhar.
- Consumir os campos `platform`, `environment`, `engine_manifest`, `diagnostics`, `actionable_messages[]` e `checks[].candidates` do `gbsdoctor --json` para tratar macOS, Windows/MSYS2 e Linux sem heuristicas no app.
- Gerar e preservar `gbastudio_project.json`; o `gbsdoctor --json` reporta `project_manifest` e valida backend, genero (`kind`), entrada, dados do projeto e assets gerados quando ele existir.
- Gerar `gbastudio_project.json.build.target` quando quiser controlar o nome da ROM; se o app nao passar `--target`, `gbsbuild` usa esse valor e cai para `game` apenas como fallback.
- Declarar `requires.engine_pack` e `requires.features` no manifesto exportado; features ausentes devem aparecer como checks `project_required_feature` falhos no JSON.
- Antes da integracao no app, o exportador deve produzir saida equivalente aos fixtures `templates/exported_topdown`, `templates/exported_platformer` e `templates/exported_isometric` do Engine Pack, conforme o genero selecionado.
- Tratar `gbastudio_engine` como backend primario privado no GBA Studio durante a maturacao, mantendo Butano apenas como backend legado/manual de rollback.
- Usar `diagnostics.butano_replacement_readiness.backend_policy == "parallel_until_manual_promotion"` como regra de produto: nenhum fluxo deve remover o rollback legado/manual apenas porque o pacote compila.
- Qualquer alteracao futura em `writeButanoSkeleton` ou no fluxo atual de export deve passar por GitNexus impact antes da edicao.

## Criterio principal de paridade

O backend `gbastudio_engine` so deve ser promovido quando o projeto completo do
GBA Studio conseguir, no mesmo fluxo:

- ser criado pelo template Exemplo GBA dentro do app;
- editar e persistir Rooms, Eventos, Sprites, Dialogos, Audio e Ajustes;
- salvar e reabrir sem perda de dados ou assets;
- exportar top-down, platformer, isometric, dungeon crawler, racing,
  point-and-click e shmup em uma unica ROM mixed;
- compilar a ROM com devkitARM e abrir a Play Window;
- executar boot, input, transicoes, dialogo, audio e troca de room sem erro.

Uma room top-down ou ROM isolada continua util como teste de componente, mas
nao comprova mais paridade do produto completo.
